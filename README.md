# AR Games Connect Internet — Relay v0.4

Стенд для проверки интернет-управления AR Games. Развитие исходной v0.2 из Diplo3/AR-Games-Relay, commit `9c6bb43df7870ca44d71e07b5144b72233c7f98f`.

## Запуск

Node.js 20 или новее. `npm install`, затем `npm start`. Страница: http://localhost:3000. Проверки: `npm test`.

Команды Render прежние: Build `npm install`, Start `node server.js`. Сервер слушает `PORT` на `0.0.0.0`; `/health` возвращает 0.4.0 и лимит телефонов. Новый сервис не нужен.

## Одна интеграция для будущих игр

Игры подключают `public/connect.js` и один раз интегрируют команды через `Client`. Для новой игры меняется только адаптер её команд и состояния. Адреса, лимиты, активный режим и паузы редактируются отдельно в корневом `relay-config.json`. Клиенты обновляют конфигурацию раз в 60 секунд, немедленно перечитывают её после обрыва и сохраняют последний рабочий вариант для временного отсутствия сети. Стабильный адрес control plane: `https://raw.githubusercontent.com/Diplo3/AR-Games-Relay/main/relay-config.json`.

При переносе Render или смене relay измените `endpoints.internet` в `relay-config.json` и опубликуйте JSON. Код игр останется прежним. Сохраните имя GitHub-репозитория и путь к файлу, либо отдельно меняйте централизованный URL в параметрах сборки. Клиенты сами переподключатся, сохраняя очереди, ID и TEAM. Не переключайте комнату во время активной игры: HOST и телефоны должны получить один и тот же маршрут.

Целевая ёмкость — 50 телефонов на комнату. Relay принимает до 50 по умолчанию; переменная Render `MAX_PHONES_PER_ROOM` меняет лимит от 1 до 100. Манифест сообщает играм целевой лимит. Повторный тест 50 телефонов × 100 команд — обязательная проверка перед релизом конкретной версии.

## Использование

1. На ноутбуке выберите HOST и комнату из 4–8 букв/цифр. Для события используйте случайный код; TEST01 предназначен для локальной проверки.
2. На телефонах откройте ссылки TEAM 1 / TEAM 2 из страницы HOST. Роль и команда выбираются из ссылки; PLAYER подключается автоматически.
3. ЖМИ 1 / ЖМИ 2 отправляют команды с назначенной команде принадлежностью. Названия кнопок не меняют TEAM.
4. Запустите 100 импульсов или задайте число и интервал. Тест приостанавливается, если нет соединения телефона или HOST. Для испытания на 50 телефонах запускайте тест на каждом.
5. Проверьте выключение сети телефона, восстановление сети, перезагрузку страницы телефона, отключение и возврат HOST. В таблице показаны ID, команда, онлайн-состояние, счётчики и RTT каждого телефона.

## Датчики и управление телефоном

`public/motion.js` содержит `SensorHub`: готовые источники ориентации/компаса, движения, акселерометра, гироскопа, линейного ускорения, гравитации, абсолютной/относительной ориентации, магнитометра, освещённости, приближения, геолокации и Gamepad. Доступность определяется на устройстве во время выполнения; Generic Sensor API поддерживает не каждый браузер/телефон. Игры также могут добавлять собственный источник через `register(name, factory)`, не меняя relay.

Разрешение сенсора запрашивается только при явном вызове `start()` из пользовательского нажатия. Для веба нужен HTTPS. Сенсорные данные идут отдельным эфемерным каналом и не занимают надёжную очередь кнопочных/игровых команд. Частота всех включённых источников вместе ограничена 20 образцами/с на телефон; relay принимает не более 25/с. Для 50 телефонов это ограничивает входящий поток примерно 1000 небольшими образцами/с. Последний образец каждого источника заменяет более старый до отправки.

Геолокация и любые будущие персональные данные не включаются автоматически: игра должна отдельно объяснить цель и запустить соответствующий источник. Relay только пересылает актуальные образцы в HOST и не сохраняет их в журнале. Камеру и микрофон не следует передавать как поток образцов через relay; если игра их запросит, используйте отдельную обработку на устройстве или специализированный медиатранспорт/WebRTC, а через relay передавайте только игровые события и компактные результаты.

ID принадлежит вкладке устройства и сохраняется при перезагрузке страницы. Разные вкладки имеют разные ID. Сессия, номер следующей команды, TEAM, очередь и статистика сохраняются в localStorage. TEAM фиксируется до конца сохранённой сессии. Для новой комнаты перезагрузите страницу без параметров и укажите другой код. Не очищайте данные браузера во время игры.

## Значение счётчиков

- Отправлено: созданные телефоном уникальные команды, включая очередь во время обрыва.
- Принято сервером: уникальные команды в текущем процессе relay.
- Получено HOST: обработка подтверждена HOST; обычный server ACK этого не гарантирует.
- Ожидает: команды, для которых ещё нет подтверждения HOST.
- Потеряно: истёк срок 30 минут или команда окончательно отклонена. Временное ожидание потерей не считается.
- Дубли: повторные попытки доставки; HOST их подтверждает без повторной обработки.
- RTT min / avg / max: за сохранённую клиентскую сессию, измеряется ping/pong к серверу, а не время обработки игры.
- Reconnect: повторные подключения; серверная таблица хранит их за время жизни процесса relay, телефон — за время работы клиента.

Статистика телефона передаётся раз в две секунды; пока телефон отключён, таблица показывает последнее полученное значение. После рестарта relay его счётчики начинаются заново; клиентские сохраняются. Поэтому серверные и клиентские накопительные значения могут различаться.

## Доставка и ограничения стенда

Протокол v0.2 сохранён для клиентов без `protocol:3`, включая прежние button/ack и ping/pong. Для надёжной доставки используйте клиент v0.3+ и на телефоне, и на HOST; старый HOST не отправляет host_ack.

v0.3 использует очередь на телефоне, повторную отправку, журнал событий relay и подтверждение обработки HOST. Ключ дедупликации — clientId + sessionId + seq. HOST хранит обработанные eventId; повтор после потери ACK или рестарта relay не вызывает повторное действие. Очередь повторяет команду с тем же seq, TEAM и sessionId.

Журнал relay хранится в памяти до 30 минут, очередь телефона — до 30 минут. Лимиты: 100 комнат, 50 устройств на комнату по умолчанию (переменная окружения — до 100), 20 000 записей журнала на комнату, 5000 ожидающих команд на телефон; WebSocket-сообщение до 16 KiB. При переполнении журнала команды ждут освобождения записей или истечения срока. После рестарта relay восстановление зависит от очереди телефона и сохранённого журнала HOST.

Это диагностический стенд: вход HOST ограничен одним соединением на комнату, но код комнаты не заменяет авторизацию. В следующем этапе нужны HOST-токены и постоянный серверный журнал для длительных событий. Пауза между выполнением действия игры и записью дедупликации при аварийном завершении HOST требует транзакционной обработки в самой игре; универсальной гарантии exactly-once для внешних действий нет.

## Electron и LAN

`public/connect.js` — общий клиент для браузера и Node/Electron. Если URL не указан, он получает адрес из удалённого манифеста, выбирает интернет или LAN и переподключается при изменении маршрута. `examples/electron-host.cjs` показывает `startHost` и `startPlayer`. Игры используют `sendCommand(action, payload)` для надёжных событий и `sendSensor(channel, sample)` для частых заменяемых измерений; HOST принимает их через `onCommand` и `onSensor`. `SensorHub` можно подключить на странице PLAYER или заменить собственным источником игры. HOST хранит eventId до подтверждения; при асинхронной обработке необходимо подтверждать ACK только после завершения действия и записи его идентификатора.

Для LAN укажите совместимый локальный WebSocket URL в `endpoints.lan`; выбранный режим задаётся настройкой, а не изменением кода игры. Если у игры собственный сетевой протокол, напишите один адаптер при первой интеграции. Исходников Electron-игры в этом репозитории нет, поэтому пример нужно перенести в игру после получения её кода. QR для комнаты формируется в игре из ссылки на страницу PLAYER.
